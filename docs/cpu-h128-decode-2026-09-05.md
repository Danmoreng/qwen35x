# CPU H128 decode experiments, 2026-09-05

The retained implementation combines blockwise H128/Q8 preparation, compact
single-token activation blocks, a persistent decode workspace, precomputed sign
words, and an AVX-512 H128 transform for decode. FP16 remains the default KV-cache
format. The Q4 checkpoint format and its payload are unchanged.

## Retained changes

- `Q8_0BlockX1` uses 40 bytes per 32 activation values, instead of using only the
  first token slot of a 152-byte `Q8_0BlockX4`. Prefill still uses X4. At a width
  of 3,584 values this reduces prepared decode scratch from 17,024 to 4,480 bytes.
  This is a scratch reduction, not a corresponding reduction in weight traffic.
- Single-token H128 preparation transforms 128 values into a local buffer and
  immediately emits four X1 blocks. It preserves the old order: unscaled H128,
  round the Q8 scale to FP16, then fold `1/sqrt(128)` into the FP32 prepared scale.
  The full-vector transform buffer and separate normalization pass are avoided.
- A session-owned workspace reuses forward, MLP, linear-attention and
  full-attention buffers. Packed projection outputs are consumed through direct
  pointers/spans. Linear-attention Q/K/V are views into the convolution output.
  The full-attention per-head Q/gate rearrangement remains necessary.
- Each H128 tensor prepares its immutable sign words at load time. Prefill
  workers share these read-only words. Without a supplied plan, the four-token
  API computes the signs once per tile/block rather than once per token.
- Decode can use eight ZMM vectors for H128. The emitted MSVC code keeps
  intermediate values in registers: inspection found no stack accesses or
  calls in the transform. Dispatch checks CPU support; AVX2/scalar fallbacks
  remain available.

The sign plan is tiny activation-transform metadata; weights are still read
directly from the existing CPU-packed artifact. No checkpoint regeneration is
needed.

## Rejected extension

The same AVX-512 transform was also tried for four-token prefill. Its apparent
initial gain did not survive repeat comparisons. Later trials favored AVX2 or
were inconclusive, so the retained prefill path uses AVX2 with shared signs.
The experiment binaries `build-cpu-h128-avx512` and `build-cpu-h128-final`
contain the rejected prefill extension; `build-cpu-h128-selected` contains the
retained version. Those build directories are local, ignored artifacts.

## Method

Machine: AMD Ryzen 9 9955HX3D, 16 cores / 32 logical processors, Windows,
MSVC 14.44, Release build. Inference uses 12 threads and explicit
`--cpu-isa avx512-vnni`, with FP16 KV cache and no prefix reuse.
Base revision: `6fc92f4844a6e4946c3ad8041f22e906cfa54956`, plus the already
present KV-cache precision changes. A separate baseline binary was built
before modifying the decode path.

All timing runs use `scripts/benchmark-inference-seq.ps1`, sequentially, with
`-Runs 3 -WarmupRuns 1 -MaxNewTokens 128 -MaxContext 256`. Decode is normal greedy
generation, not teacher forcing. `decode1` starts with token 1; `decode128`
uses the first 128 tokens of `configs/qwen3_5_0_8b_text_1024x512_tokens.csv`.
`prefill256` uses the first 256 tokens and `-PrefillOnly`.

The final retained-version comparison runs baseline / selected / selected /
baseline separately for each workload, giving six measured runs per variant.
Results are medians of per-run throughput. The CSV retains exploratory and
repeat measurements as well, including unfavorable results. Short runs on
this machine show appreciable temporal variation; individual stage effects
must not be inferred simply by subtracting the exploratory medians.

## Results

The retained changes provide only a small measured decode improvement under
controlled CPU placement. They do **not** establish a large or universal
throughput gain. Unrestricted measurements fluctuate substantially, including
regressions for the short prompt; all runs are retained in the companion CSV.

After the unrestricted trials, a placement-controlled comparison used the
same `0x0000ffff` process affinity mask (logical processors 0-15) for both
binaries, still with 12 worker threads. The PowerShell benchmark process set
its own affinity temporarily and restored it in `finally`; child-process
inheritance was verified on a running qwen35x process (mask 65535). This is
only an experimental control, **not** a new engine default. Absolute speeds
from this control must not be compared with unrestricted runs.

Controlled placement, six measurements per cell:

| Workload | Baseline token/s | Retained token/s | Change |
|---|---:|---:|---:|
| Decode, 1 prompt token | 123.79 | 124.70 | +0.74% |
| Decode, 128 prompt tokens | 122.05 | 123.42 | +1.13% |
| Prefill, 256 tokens | 966.63 | 959.57 | -0.73% |

The small prefill difference is within the observed spread; no prefill speedup
is claimed. Even the controlled decode gain is small relative to run variation,
so these six-run medians are observations, not a statistical guarantee.

Final unrestricted comparison, also six measurements per cell:

| Workload | Baseline token/s | Retained token/s | Change |
|---|---:|---:|---:|
| Decode, 1 prompt token | 133.10 | 126.78 | -4.75% |
| Decode, 128 prompt tokens | 131.03 | 134.96 | +3.00% |
| Prefill, 256 tokens | 1209.62 | 1202.16 | -0.62% |

These changes save activation scratch, allocations, copies and transform work;
the remaining weight reads and projection kernels still dominate. The trials
do not isolate reliable additive gains for each change. The compact layout and
fusion were tested together, followed by workspace reuse, sign reuse, and then
the AVX-512 transform. Early exploratory medians should not be treated as
independent improvement percentages.

## Correctness and build validation

- All seven CTest suites pass, including fused preparation comparisons across
  scalar/AVX2/VNNI/AVX-512 requests, multiple seeds and widths, zeros, and cached
  versus on-demand signs. Both single-token and four-token APIs are covered.
- Before/after full-model logits are byte-identical for 1-, 65- and 128-token
  prompts followed by three teacher-forced tokens, separately for AVX2 and
  AVX-512-VNNI. This covers tiled prefill and its one-token remainder.
- The retained version also produces byte-identical logits with both canonical
  and CPU-packed H128 checkpoints. For the 65-token AVX-512-VNNI case the logits
  dump SHA-256 is
  `cc4be03c049123a5360f75ed3cd1019e73e0978ffa069fcae236da2594313c1c`.
- Every recorded greedy sequence matches between variants within its workload,
  including all 128 output tokens.
- The persistent-session model test passes prefix replay and FP16/FP32 cache
  switches. This exercises repeated reuse of the new workspace.
- CPU test builds and the normal CUDA-enabled `build/qwen35x.exe` build pass.
  CUDA performance was not measured.

The benchmark binary for the retained source is
`build-cpu-h128-selected/qwen35x.exe`. The normal executable is rebuilt at
`build/qwen35x.exe`.

## Reproduction and artifacts

The companion [CSV](cpu-h128-decode-2026-09-05.csv) contains all measured runs;
`benchmarks/h128-stage-profiles` holds the local full JSON profiles. Labels
`selected-*` identify the final unrestricted comparison and `affinity0000ffff-*`
the placement-controlled comparison. Labels `baseline`, `fused-compact`,
`workspace`, `signs`, `avx512` identify the initial cumulative experiments;
`confirm-*`, `final-*` and `prefill-check-*` are the follow-up trials of the
version that still enabled AVX-512 prefill.

Example unrestricted decode measurement (repeat for the baseline executable):

```powershell
.\scripts\benchmark-inference-seq.ps1 `
  -Executable build-cpu-h128-selected/qwen35x.exe `
  -Modes cpu-h128 `
  -CpuQ4H128 models/qwen3.5-0.8b/model-q4-h128-cpu-x8.q35h `
  -CpuThreads 12 -CpuIsa avx512-vnni -CpuKvCache fp16 `
  -PromptMode prompt-tokens -PromptTokensCsv '1' -PromptName decode1 `
  -Runs 3 -WarmupRuns 1 -MaxNewTokens 128 -MaxContext 256 `
  -RunLabel reproduction-selected -CsvOut benchmarks/h128-reproduction.csv
```

Before-change source snapshots and all experimental builds are kept locally
under `benchmarks/h128-snapshots` and `build-cpu-h128-*`. The checkpoint used is
`models/qwen3.5-0.8b/model-q4-h128-cpu-x8.q35h`, SHA-256
`ba3fa90884e6fd4690a40c45af982c3ca9a38badb05ae865d4597fe71efe1cde`.
